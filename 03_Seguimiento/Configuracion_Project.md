## 3. Campos recomendados

| Campo | Tipo | Valores o uso |
| --- | --- | --- |
| Status | Selección única | Pendiente, En curso, Bloqueada, En revisión, Finalizada |
| Prioridad | Selección única | Alta, Media, Baja |
| Línea de trabajo | Selección única | Planeación y directorio, Difusión digital, Jornadas presenciales |
| Fecha de inicio | Fecha | Fecha acordada por el equipo |
| Fecha objetivo | Fecha | Fecha de compromiso aprobada |

Los nombres y opciones disponibles dependen de la configuración del Project. **Assignees** se gestiona desde cada Issue y solo funciona para cuentas con acceso al repositorio.

## 4. Vistas recomendadas

- **Tabla de seguimiento:** título, responsable, Status, Prioridad, Línea de trabajo y fechas.
- **Tablero Kanban:** agrupado por Status para visualizar actividades pendientes, en curso, bloqueadas, en revisión y finalizadas.
- **Cronograma / Roadmap:** usar únicamente cuando el equipo haya acordado fechas de inicio y cierre.

## 5. Límite de configuración y pasos manuales

La conexión GitHub disponible para esta intervención permite consultar y modificar archivos e Issues, pero no expone operaciones para editar directamente los campos y vistas de GitHub Projects (Projects V2). Por ello, esta guía documenta la configuración objetivo, pero **no afirma que el tablero ya tenga esos campos o vistas**.

Para completar la configuración desde la interfaz de GitHub:
1. Abrir el Project y entrar a la vista de tabla.
2. En el menú de campos, agregar **Status**, **Priority**, **Iteration** si el equipo la utiliza, y campos personalizados **Línea de trabajo**, **Fecha de inicio** y **Fecha objetivo**.
3. Configurar las opciones de Status y Línea de trabajo según las tablas anteriores.
4. Crear una vista Board agrupada por Status.
5. Crear una vista Roadmap solo después de acordar fechas reales.
6. Incorporar los 15 Issues existentes y comprobar que cada tarjeta conserve su enlace al Issue.

## 6. Reglas de actualización

1. Actualizar el estado cuando exista un cambio real y verificable.
2. Registrar en el Issue el avance, bloqueo, decisión y siguiente acción.
3. No marcar una actividad como finalizada solo por haber creado una carpeta o un documento preliminar.
4. Cerrar el Issue cuando el criterio de aceptación esté cumplido y la evidencia esté enlazada.
5. No incorporar al tablero ni a los comentarios datos personales o sensibles de jóvenes atendidos.

## 7. Cronograma, metas e indicadores pendientes

No se asignaron fechas de inicio ni fechas objetivo porque no hay un cronograma aprobado disponible en los Issues revisados. Las metas numéricas, cobertura, línea base y periodicidad también deben ser acordadas por el equipo antes de ingresarlas al Project.

La matriz de indicadores propone fórmulas y fuentes, pero no contiene resultados observados. Para cada indicador, el equipo debe validar denominador, periodo, meta, responsable de reporte y fuente institucional. No se deben inventar porcentajes ni presentar metas sugeridas como compromisos aprobados.

## 8. Rutina de seguimiento

En cada corte acordado por el equipo:
- revisar tareas próximas, vencidas y bloqueadas;
- confirmar avances con responsables;
- comprobar dependencias;
- revisar entregables y evidencias;
- actualizar riesgos y decisiones;
- acordar acciones, responsables y fechas siguientes.

La frecuencia del corte debe definirse con el equipo; esta guía no presupone una periodicidad ya aprobada.
